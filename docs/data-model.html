01  문제

주문을 하나씩 판정하면 반드시 틀린다

가용재고 1개를 두 주문이 각각 1개씩 필요로 하면, 따로 계산했을 때 둘 다 “준비 가능”이 나온다. 실제로 나갈 수 있는 건 한 건이다.

이게 이 과제에서 가장 틀리기 쉬운 지점이고, 설명을 여기서 시작해야 하는 이유다. 재고 조회는 누구나 짤 수 있지만, 여러 주문이 같은 재고를 나눠 갖는 순간 계산의 성격이 달라진다. 주문별 독립 계산은 화면에 “바로 준비 가능 3건”을 띄우고, 담당자는 3건을 약속한 뒤 1건만 내보내게 된다.

주문마다 따로 계산
  1. ORD-A 가용재고 조회2
  2. ORD-B 가용재고 조회2
  3. ORD-C 가용재고 조회2
셋 다 “준비 가능”. 같은 2개를 세 번 약속했다. 재고는 아무도 건드리지 않았으니 조회할 때마다 2가 나온다.
원장에서 순서대로 차감
  1. 원장 개설2
  2. ORD-A 1개 배정1
  3. ORD-B 1개 배정0
  4. ORD-C 배정 불가0
A·B는 준비 가능, C는 부족. 앞 주문이 가져간 몫이 뒤 주문의 계산에 이미 반영돼 있다.

그래서 판정 함수는 주문 하나를 받지 않는다. 준비 대상 주문 전체를 한 번에 받아, 원장(AllocationLedger)을 한 번만 만들고 배송일 순서로 물려준다. 원장은 의도적으로 가변이다 — 순차 배정은 본질적으로 누적 상태이기 때문이다. 대신 수명을 planPreparation() 호출 하나 안으로 묶어, 바깥의 어떤 값도 바뀌지 않게 했다.

02  데이터 설계

세 가지 원칙이 나머지를 결정했다

파생값은 저장하지 않는다

가용재고·잔여수량은 필드가 아니라 함수다. 현재고만 바꾸고 가용재고 갱신을 잊는 실수가 구조적으로 불가능해야 한다.

✗ inventory.availableQuantity
✓ getAvailableQuantity(inventory)

타입은 시트와 1:1

파일 하나가 시트 하나다. 엑셀을 다시 내보내도 같은 자리에 대응된다. 한글 상태값은 리터럴 유니온이라 시트에 없는 값을 쓰면 컴파일이 막는다.

'작성 중' | '발주 확정' | '진행 중' | …

규칙은 순수 함수로

재고 숫자를 바꾸는 모든 규칙이 React도 스토어도 모른다. 그래서 브라우저 없이 검증되고, 같은 입력에 항상 같은 판정이 나온다.

domain/ → data/ → types/ (역방향 import 없음)

엑셀에서 손댄 것은 두 가지뿐이다. 날짜는 엑셀 float 오차로 생긴 15:59:59.999999 꼬리를 초 단위로 반올림하고 타임존을 명시했다 (16:00:00+09:00). 예/아니오는 시리얼관리여부·출고대상여부·확정여부 세 칸만 boolean으로 바꿨다. 나머지 한글 상태값은 화면에 그대로 나가므로 시트 값을 유지한다.

04  원장 배정 — 실제 숫자

같은 품목, 같은 창고, 다른 판정

설명할 때 이 표 하나만 보여주면 된다. MAT-Z10-Q(Z10 매트리스 Q)를 본사물류창고에서 요구하는 주문 넷이다. 시트에 적힌 현재고는 3, 예약수량은 1이므로 가용재고는 2. 입고예정은 MO-20260721-Z10 2개가 07-22 도착 예정이다.

원장이 보여준 것 이 주문이 가져간 것
순위 주문번호 배송예정일 필요 가용재고 입고예정 재고에서 예정에서 부족 판정
4 ORD202607200001 07-22 1 2 0 1 0 0 READY
9 ORD202607200002 07-23 1 1 2 1 0 0 READY
10 ORD202607200007 07-23 1 0 2 0 1 0 WAITING
25 ORD202607210029 07-27 1 0 1 0 1 0 WAITING
가용재고 잔액
2→1→0→0
입고예정 잔여
2→2→1→0

순위 4와 9는 같은 재고에서 1개씩 가져갔다. 두 번째 주문의 가용재고가 2가 아니라 1로 보이는 것이 원장의 전부다. 세 번째 주문에 오면 재고가 0이라 입고예정에서 당기고, 그래서 판정이 READY가 아니라 WAITING이 된다 — 물건은 확보됐지만 아직 창고에 없다.

왜 첫 줄만 입고예정이 0인가

MO-20260721-Z10은 네 주문 모두에게 존재하지만, 순위 4에게는 보이지 않는다. 07-22에 도착하는 물량은 배송일이 07-22인 주문을 맞출 수 없기 때문이다. 입고 검수와 적치를 거쳐야 피킹할 수 있으므로 배송일 전날까지 들어와야 쓸 수 있다 (isUsableBy).

이 조건이 빠지면 배송일 뒤에 도착하는 발주까지 대기 근거로 잡혀서, 사실은 못 맞추는 주문이 ‘입고 대기’로 보인다. 발주가 나가야 할 주문이 조용히 묻히는 쪽이 훨씬 위험하다. 같은 이유로 입고예정은 합계 하나로 들지 않고 문서별 잔여를 따로 추적한다 — 사용 가능 여부가 주문마다 다르므로, 합계로 뭉치면 이 구분이 사라진다.

05  상태 판정

네 가지 결론은 한 줄에서 갈린다

부족 = 필요 − 가용재고 − 입고예정
상태 언제 담당자가 할 일 시드 결과
READY 가용재고만으로 전량 충당 예약 → 출고 10건
WAITING 부족은 0이지만 입고예정에서 당겼다 기다린다 — 검사·입고가 끝나면 자동으로 재판정 5건
SHORTAGE 원장을 다 긁어도 부족이 남는다 발주 — 부족수량이 곧 발주수량 8건
EXCEPTION 판정 자체가 불가능 데이터를 고친다 — 자동 처리하지 않는다 3건

EXCEPTION은 재고를 한 개도 잡지 않는다

미등록 품목·사용 중지 창고·수량 0·세트 구성 오류는 계산이 성립하지 않는 상태다. 이때 정상 품목까지 배정해 두면, 담당자가 데이터를 고쳐 다시 판정할 때 이미 자기 몫을 잡아버린 상태가 되어 부족분이 실제보다 작게 나온다. 그래서 오류가 하나라도 있으면 원장을 건드리지 않고 되돌린다.

같은 이유로 EXCEPTION 주문에는 품목별 숫자를 내지 않는다. 사용 중지 창고 주문에 ‘구창고에 5개 있음’을 같이 띄우면 낼 수 있다는 오해를 부른다.

06  상태 전이

재고를 움직이는 여섯 동작이 각각 무엇을 바꾸는가

판정은 읽기만 한다. 숫자를 실제로 바꾸는 건 이 여섯 개뿐이고, 어느 칸이 움직이는지가 전부 다르다. 이 표가 데이터 모델의 요약이다.

동작 현재고 예약수량 개체상태 (05_개체재고) 문서 (07_입고예정)
예약 그대로 + 소요량 창고 보관 중 → 주문 배정됨 —
예약 해제 그대로 − 소요량 주문 배정됨 → 창고 보관 중 —
출고 − 소요량 − 소요량 주문 배정됨 → 출고 완료 —
발주 그대로 그대로 그대로 문서 생성 (PO / MO)
품질검사 그대로 그대로 그대로 검사상태 → 검사 완료
입고 + 입고수량 그대로 신규 개체 생성 입고수량 누적

읽는 법 세 가지. 예약은 현재고를 줄이지 않는다 — 물건은 아직 창고에 있고, 다른 주문이 못 쓰게 잡아두는 것뿐이다. 실제 차감은 출고에서 일어난다. 발주는 아무 숫자도 바꾸지 않는다 — 문서를 만든 것만으로 현재고는 늘지 않는다. 입고만 현재고를 늘린다, 그리고 그것이 대기 중인 주문을 풀어주는 유일한 트리거다.

예약은 전량 아니면 전무다. 한 품목이라도 모자라면 아무것도 잡지 않는다. 수량은 맞는데 배정할 개체가 부족하면 04_재고현황과 05_개체재고가 어긋난 상태이므로, 절반만 반영하지 않고 SERIAL_SHORTAGE로 되돌린다.

07  중복 처리

같은 요청이 두 번 와도 재고는 한 번만 움직인다

서버가 없는 프로젝트라 트랜잭션·row lock·idempotency key를 인메모리 구조로 옮겼다. 스토어 액션 하나가 트랜잭션 경계다 — 도메인 함수가 돌려준 컬렉션을 set() 한 번에 통째로 대입한다. 재고와 개체를 따로 두 번 대입하면 그 사이에 렌더가 끼어 04와 05가 어긋난 중간 상태가 화면에 보인다.

멱등성의 근거는 두 겹이다. 각 동작이 자기 상태만으로 중복을 막으면 빈틈이 생긴다 — 예약은 Reservation 기록으로 막히지만, 입고는 같은 문서에 3개를 두 번 넣어도 둘 다 정당한 부분 입고로 보인다. 그래서 요청 ID를 판정 근거로 따로 둔다.

요청 ID는 화면이 만든다. 성공한 뒤에만 올라가는 토큰이라, 같은 버튼을 두 번 누르면 토큰이 같아 두 번째가 막히고, 담당자가 일부러 다시 입고하는 경우에는 토큰이 올라가 정당한 새 요청이 된다. 시각이나 난수로 만들면 이 구분이 사라진다.

08  말하는 순서

같은 내용을 3분과 15분으로

3분 — 결론부터
  1. 문제 한 문장. “주문 26건이 같은 재고를 놓고 경쟁한다. 무엇을 오늘 내보낼 수 있는가를 정하는 계산이다.”
  2. 함정 하나. 가용재고 1개, 두 주문이 각각 1개. 따로 계산하면 둘 다 준비 가능이 나온다.
  3. 해법 한 줄. 원장을 한 번 만들고 배송일 순서로 차감한다.
  4. 표 하나. 04번 절의 네 줄. 가용재고가 2 → 1 → 0으로 깎이는 것만 짚는다.
  5. 신뢰 근거. 엑셀 971셀 대조, 테스트 217개.
15분 — 설계 이유까지
  1. 위 3분을 그대로 먼저 한다.
  2. 데이터 설계 3원칙. 파생값 저장 안 함 · 시트와 1:1 · 순수 함수. 각각 “안 그러면 무슨 사고가 나는지”로 설명한다.
  3. 파이프라인 6단계. 순서에 이유가 있다는 것만 — 특히 가용재고를 입고예정보다 먼저 쓰는 이유.
  4. 배송일 전날 규칙. 04번 절의 첫 줄만 입고예정이 0인 이유. 이 디테일 하나가 업무를 이해했다는 신호다.
  5. 상태 전이표. 예약은 현재고를 안 줄인다 / 발주는 아무것도 안 바꾼다.
  6. 멱등성. 왜 상태 기록만으로 부족하고 요청 ID가 따로 필요한가.

피해야 할 설명 순서

화면부터 보여주면 안 된다. 화면은 계산 결과를 늘어놓은 것이라, 보는 사람이 “재고 목록 만들었네”로 이해하고 끝난다. 함정을 먼저 던지고 해법을 보여주는 순서여야 원장이 왜 필요한지가 전달된다. 폴더 구조 설명도 마지막이다 — 구조는 원칙의 결과이지 원칙이 아니다.
