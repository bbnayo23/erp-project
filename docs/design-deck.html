    • 01 · 문제 정의

    재고 조회는 누구나 짭니다

    난이도는 여러 주문이 같은 재고를 나눠 갖는 순간 생깁니다.

    한 주문만 놓고 보면 가용재고를 읽어 필요량과 비교하면 끝입니다. 주문이 26건이 되면 계산의 성격 자체가 달라집니다.

  • 여기서 한 번 멈춥니다. 듣는 사람이 "그게 왜 어렵지?"를 스스로 묻게 만드는 슬라이드입니다.
  • 말할 문장: "주문 하나를 판정하는 함수는 30분이면 짭니다. 그 함수를 26번 부르면 틀린 답이 나옵니다."
  • 다음 슬라이드에서 왜 틀리는지 숫자로 보여준다고 예고합니다.

    • 01 · 함정

    따로 계산하면 같은 재고를 세 번 약속합니다

    주문마다 따로 계산
    1. ORD-A 가용재고 조회2
    2. ORD-B 가용재고 조회2
    3. ORD-C 가용재고 조회2

    셋 다 "바로 준비 가능". 아무도 재고를 건드리지 않았으니 조회할 때마다 2가 나옵니다. 화면은 3건을 약속하고 실제로는 1건만 나갑니다.

    원장에서 순서대로 차감
    1. 원장 개설2
    2. ORD-A 1개 배정1
    3. ORD-B 1개 배정0
    4. ORD-C 배정 불가0

    A·B는 준비 가능, C는 부족. 앞 주문이 가져간 몫이 뒤 주문의 계산에 이미 반영돼 있습니다.

  • 이 슬라이드가 발표의 심장입니다. 왼쪽을 손으로 짚으면서 "가용재고 2를 세 번 읽었습니다"라고 말합니다.
  • 오른쪽은 숫자가 2 → 1 → 0으로 깎이는 것만 짚습니다. 그게 원장의 전부입니다.
  • 말할 문장: "담당자에게 이건 단순한 버그가 아닙니다. 3건을 약속하고 1건만 내보내는 사고입니다."

    • 01 · 해법

    원장을 한 번 만들고 배송일 순서로 물려줍니다

    판정 함수는 주문 하나를 받지 않습니다. planPreparation()이 준비 대상 26건을 한 번에 받아 AllocationLedger를 한 번만 만들고, 배송예정일 순서로 차감하며 판정합니다.

    순서는 배송예정일

    같으면 주문접수일시, 그것도 같으면 주문번호. 세 번째는 업무 규칙이 아니라 결정성을 위한 것입니다.

    원장은 가변, 수명은 한 호출

    순차 배정은 본질적으로 누적 상태입니다. 대신 수명을 호출 하나 안에 묶어 바깥 값은 안 바뀝니다.

    입고예정은 문서별로

    합계로 뭉치면 "이 배송일에 쓸 수 있는가"를 문서마다 따로 판단할 수 없습니다.

  • 세 번째 정렬 키를 꼭 말하세요. "동순위가 실행마다 다른 순서로 배정되면 같은 데이터에서 다른 판정이 나옵니다. 테스트도 재고 정합성도 믿을 수 없습니다." — 결정성을 의식했다는 신호입니다.
  • "원장이 가변"은 먼저 말하는 게 좋습니다. 불변성을 지적받기 전에 왜 그렇게 했는지, 어떻게 가둬뒀는지를 설명합니다.
  • 입고예정을 문서별로 쪼갠 이유는 다음 슬라이드에서 실제 숫자로 이어집니다.

    • 01 · 실제 데이터

    같은 품목, 같은 창고, 다른 판정

    Z10 매트리스 Q · 본사물류창고. 현재고 3, 예약 1 → 가용재고 2. 입고예정 MO-20260721-Z10 2개가 07-22 도착 예정입니다.

    원장이 보여준 것 이 주문이 가져간 것
    순위 주문번호 배송 필요 가용재고 입고예정 재고에서 예정에서 판정
    4 ORD202607200001 07-22 1 2 0 1 0 READY
    9 ORD202607200002 07-23 1 1 2 1 0 READY
    10 ORD202607200007 07-23 1 0 2 0 1 WAITING
    25 ORD202607210029 07-27 1 0 1 0 1 WAITING
    가용재고 잔액 2→1→0→0 입고예정 잔여 2→2→1→0
  • 표 하나만 보여주면 됩니다. 순위 4와 9가 같은 재고에서 1개씩 가져갔다는 것, 그래서 두 번째 주문의 가용재고가 2가 아니라 1로 보인다는 것 — 이게 원장의 전부입니다.
  • 세 번째 줄에서 판정이 READY가 아니라 WAITING이 되는 이유를 말합니다. "재고가 0이라 입고예정에서 당겼습니다. 물건은 확보됐지만 아직 창고에 없습니다."
  • 모든 수치는 실제로 실행해 뽑은 값입니다. 질문받으면 pnpm test로 재현된다고 답합니다.
  • 다음 슬라이드로 넘어가기 전에 "첫 줄만 입고예정이 0인 게 보이시나요?"로 미끼를 던집니다.

    • 01 · 디테일

    배송일 전날까지 들어와야 쓸 수 있습니다

    07-22 도착 물량은 배송일이 07-22인 주문을 맞출 수 없습니다.

    입고 검수와 적치를 거쳐야 피킹할 수 있습니다. 그래서 순위 4에게는 같은 문서가 보이지 않습니다 — isUsableBy가 하루를 요구합니다.

    이 조건이 빠지면

    배송일 뒤에 도착하는 발주까지 대기 근거로 잡혀, 사실은 못 맞추는 주문이 '입고 대기'로 보입니다.

    더 위험한 쪽

    발주가 나가야 할 주문이 조용히 묻히는 것. 그래서 판정을 느슨하게가 아니라 엄하게 잡았습니다.

  • 이 디테일 하나가 "업무를 이해했다"는 신호로 가장 잘 작동합니다. 시간이 없어도 이 슬라이드는 버리지 마세요.
  • 말할 문장: "두 판정 중 어느 쪽으로 틀리는 게 덜 위험한지를 기준으로 정했습니다. 못 맞추는데 대기로 보이는 쪽이 훨씬 위험합니다."
  • 여기서 입고예정을 문서별로 추적하는 이유가 완성됩니다. 합계로 뭉치면 문서마다 다른 이 판단이 사라집니다.

    • 02 · 데이터 설계

    세 원칙이 나머지를 결정했습니다

    파생값은 저장하지 않는다

    가용재고·잔여수량은 필드가 아니라 함수입니다. 갱신을 잊는 실수가 구조적으로 불가능해야 합니다.

    ✗ inventory.availableQuantity
    ✓ getAvailableQuantity(inventory)

    타입은 시트와 1:1

    파일 하나가 시트 하나. 한글 상태값은 리터럴 유니온이라 시트에 없는 값을 쓰면 컴파일이 막습니다.

    '작성 중' | '발주 확정' | '진행 중' | …

    규칙은 순수 함수

    재고를 바꾸는 모든 규칙이 React도 스토어도 모릅니다. 브라우저 없이 검증되고 같은 입력에 같은 판정이 나옵니다.

    domain → data → types (역방향 없음)

  • 각 원칙을 "안 그러면 무슨 사고가 나는지"로 설명하세요. 원칙만 나열하면 교과서 낭독이 됩니다.
  • 파생값: "현재고만 고치고 가용재고 갱신을 잊는 버그를 만들 수 없게 했습니다. 필드가 없으니까요."
  • 1:1: "엑셀을 다시 내보내도 같은 자리에 대응됩니다. 실제로 971셀을 자동 대조합니다" — 뒤 슬라이드 예고.
  • 순수 함수: "그래서 도메인 테스트 190여 개가 브라우저 없이 1초 안에 돕니다."

    • 02 · 계층

    의존 방향이 한쪽으로만 흐릅니다

    app → pages → features → { components, store } → domain → data → types
                                                    ↓             ↑
                                                  utils ──────────┘

    domain 은 상위를 모른다

    React·zustand를 import하지 않습니다. 그래서 화면을 다 바꿔도 재고 로직은 그대로입니다.

    features 가 한글을 갖는다

    도메인은 코드값만 압니다. 문구를 고치는 일이 판정 로직을 건드리지 않습니다.

    페이지는 마크업만

    화면당 hooks.ts가 상태·액션·표시용 가공을 맡고, 페이지 .tsx에는 계산이 없습니다.

  • 다이어그램은 3초만 보여주고 넘어갑니다. 화살표를 하나씩 읽으면 지루해집니다.
  • 한 문장으로: "재고 숫자를 바꾸는 규칙은 전부 domain 23개 파일에 있고, 그 파일들은 React를 모릅니다."
  • 구조를 자랑하지 말고 구조가 막아주는 실수를 말하세요. "화면에서 재고를 계산하면 스토어가 다시 확인하는 의미가 없어집니다."

    • 02 · 파이프라인

    주문 한 건이 판정에 이르는 여섯 단계

    1groupOrderRows 시트 37행 → 주문 29건엑셀은 주문 하나를 품목별 여러 행으로 갖고 있다
    2isPreparationTarget '주문 확정' 26건만 남긴다취소·완료 주문을 넣으면 진짜 데이터 오류와 섞인다
    3sortOrdersByPriority 배송예정일 → 접수일시 → 주문번호세 번째는 결정성을 위한 것
    4expandBundle 세트를 구성품으로 풀고 서비스를 뺀다구성이 비었거나 순환이면 조용히 버리지 않고 오류로 세운다
    5allocate 가용재고 먼저, 모자란 만큼만 입고예정순서를 바꾸면 지금 나갈 수 있는 주문이 도착을 기다린다
    6worstStatus 품목 중 가장 나쁜 상태가 주문의 상태한 품목이라도 부족하면 그 주문은 못 나간다
  • 여섯 개를 다 읽지 마세요. 4번과 5번만 짚습니다.
  • 4번: "세트 구성이 비어 있으면 소요량이 0이 됩니다. 조용히 버리면 준비 가능한 주문처럼 보이므로 오류로 세웁니다."
  • 5번: "가용재고를 입고예정보다 먼저 쓰는 게 중요합니다. 반대로 하면 지금 당장 나갈 수 있는 주문이 도착을 기다리게 됩니다."
  • 나머지는 "순서에 각각 이유가 있는데 시간상 두 개만 말씀드렸습니다"로 넘깁니다.

    • 02 · 판정

    네 가지 결론은 한 줄에서 갈립니다

    부족 = 필요 − 가용재고 − 입고예정
    상태 언제 담당자가 할 일 시드 결과
    READY 가용재고만으로 전량 충당 예약 → 출고 10건
    WAITING 부족은 0이지만 입고예정에서 당겼다 기다린다 — 입고되면 자동 재판정 5건
    SHORTAGE 원장을 다 긁어도 부족이 남는다 발주 — 부족수량이 곧 발주수량 8건
    EXCEPTION 판정 자체가 불가능 데이터를 고친다 — 자동 처리 안 함 3건
  • 공식 한 줄을 먼저 읽고, 표는 WAITING과 SHORTAGE의 차이만 짚습니다. "둘 다 지금은 못 나가지만, 하나는 기다리면 되고 하나는 발주해야 합니다."
  • 시드 결과 10/5/8/3을 보여주는 이유: 네 상태가 모두 나오는 데이터로 검증했다는 뜻입니다. 그 말을 꼭 하세요.
  • 부족수량이 곧 발주수량이라는 점 — 발주 화면이 별도 계산을 하지 않는다는 근거입니다.

    • 02 · 예외 처리

    EXCEPTION 은 재고를 한 개도 잡지 않습니다

    미등록 품목 · 사용 중지 창고 · 수량 0 · 세트 구성 오류는 계산이 성립하지 않는 상태입니다.

    정상 품목까지 배정해 두면 데이터를 고쳐 다시 판정할 때 부족분이 실제보다 작게 나옵니다.

    그래서 되돌린다

    오류가 하나라도 있으면 원장을 건드리지 않고 그대로 반환합니다.

    숫자도 내지 않는다

    사용 중지 창고 주문에 '구창고에 5개 있음'을 띄우면 낼 수 있다는 오해를 부릅니다.

    자동으로 고치지 않는다

    임의로 대체 창고를 고르거나 수량을 보정하면 담당자가 사고를 모르게 됩니다.

  • 이 슬라이드는 "자동화하지 않기로 한 결정"을 보여줍니다. 과제에서 판단력을 드러내는 자리입니다.
  • 말할 문장: "고칠 수 있는 것도 고치지 않았습니다. 담당자가 알아야 하는 사건이라고 봤습니다."
  • 부족분이 작게 나오는 시나리오를 한 번 풀어 말하면 설득력이 큽니다. "자기 몫을 이미 잡아버린 상태에서 다시 계산하니까요."

    • 03 · 상태 전이

    여섯 동작이 각각 어느 칸을 바꾸는가

    동작 현재고 예약수량 개체상태 입고예정 문서
    예약 그대로 + 소요량 보관 중 → 주문 배정됨 —
    예약 해제 그대로 − 소요량 주문 배정됨 → 보관 중 —

    검사 통과 ──→ 입고 ──→ 예약 ──→ 출고
    │           │         │
    │           │         └ 예약해야 출고할 수 있다
    │           └ 입고하면 대기 주문이 준비 완료로 재판정된다
    └ 통과시켜야 입고할 수 있다
