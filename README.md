# 재고 흐름 ERP

기준 시각 **2026-07-21 09:00** 의 창고 스냅샷에서, 확정 주문을 배송일 순으로 훑어
**준비 가능 여부를 판정 → 예약 · 피킹 · 출고(재고 감소)** 하거나
**부족분 발주 → 입고(재고 증가)** 하는 흐름을 세 화면으로 운영한다.

백엔드 없는 프론트엔드 단일 프로젝트다. 재고를 바꾸는 규칙은 전부 순수 함수이고
`pnpm test` 로 검증된다.

| 화면     | 답하는 질문                                            | 경로       |
| -------- | ------------------------------------------------------ | ---------- |
| **제품** | 지금 창고에 무엇이 얼마나 있고, 그 숫자를 믿을 수 있나 | `/items`   |
| **주문** | 그 재고로 무엇을 내보낼 수 있고, 다음에 뭘 하나        | `/orders`  |
| **발주** | 모자란 것을 어떻게 채우고, 채워지면 무엇이 풀리나      | `/inbound` |

## 2. 세트 전개와 준비 가능 여부 계산

### 세트 전개 (`domain/order/`)

```
주문 라인
  → 취소 품목 제외
  → 세트를 구성품으로 전개 (재귀 — 중첩 세트도 끝까지)
  → 서비스 · 출고대상 아님 제외
  → 품목별 합산            ← 일반 라인과 세트 구성품의 같은 품목은 더한다
```

전개 중 만난 문제는 버리지 않고 따로 모은다 — 미등록 품목, 순환 참조 세트, 구성품 없는
세트. 조용히 버리면 준비 가능한 주문처럼 보인다.

### 준비 가능 여부 판정 (`domain/preparation/`)

주문을 하나씩 따로 판정하면 안 된다. 가용재고 1개를 두 주문이 각각 필요로 하면 둘 다
"준비 가능" 으로 나오지만 실제로 나가는 것은 한 건이다. **배정 원장**을 한 번 세우고
배송일 순서대로 물려준다.

```
정렬: 배송예정일 ASC → 주문접수일시 ASC

for 주문 in 정렬된 주문:
    for 품목 in 소요량:
        가용재고에서 먼저 쓰고, 모자라면 입고예정에서 당긴다   ← simulate (원장 미변경)

    판정 = 부족분 있으면   재고 부족
           입고예정 썼으면 대기
           아니면          바로 준비 가능

    if 판정 != 재고 부족:
        원장에서 실제로 덜어낸다                             ← commit
```

**입고예정을 쓸 수 있는 조건** — 넷을 모두 만족해야 한다.

```
확정된 문서 (확정여부 = 예)
사용 중인 창고 · 주문의 출고창고와 일치
사용가능예정일 <= 배송예정일 − 1일
잔여수량(계획 − 입고) > 0
```

준비상태는 화면에서 6종, 코드에서 4종이다. 판정 로직에서 취급이 같아 내부는 `WAITING`
하나에 사유를 붙여 들고 있지만, 화면 문구는 `품질검사 대기` · `생산 완료 대기` ·
`구매 입고 대기` 로 갈린다 — '입고 대기' 한 마디로 뭉치면 언제 풀릴지 가늠할 수 없다.
사유가 겹치면 **가장 오래 걸리는 단계**를 대표로 보여준다.

### 설계 결정: 재고 부족 주문은 재고를 선점하지 않는다

부족 판정을 받은 주문은 원장을 소진하지 않는다. 근거는 _"일부 품목만 가능하다면 그 주문의
일부 수량을 먼저 잡아두지 않습니다"_ 이고, 이 규칙은 예약뿐 아니라 **판정에도** 적용된다.
부족한 주문이 절반을 붙잡으면 그 재고로 전량 준비할 수 있었던 뒤 주문까지 막힌다.

대가는 배송일이 늦은 주문이 먼저 가져갈 수 있다는 것이다. 의도된 맞바꿈이다.

판정을 마쳐야 그 주문이 부족한지 알 수 있으므로 계산과 반영을 같은 함수에서 할 수 없다 —
`allocate` 를 `simulate` + `commit` 으로 나눈 이유다.

> 이 규칙을 빠뜨려 `ORD202607200027` 이 `재고 부족` 으로 잘못 나왔고, 골든 파일 테스트가
> 그 한 건을 짚어냈다.

### 예약한 주문은 배정 경쟁에서 빠진다

예약수량은 이미 다른 주문의 가용재고에서 빠져 있다. 그 주문을 다시 원장에 넣으면 자기
예약 때문에 자기가 부족해진다 — 현재고 5 중 3을 예약하면 가용은 2 인데 소요는 여전히 3
이라 `재고 부족` 이 되고, 있는 재고를 두고 발주가 나간다.

## 3. 부족수량 계산과 발주 · 입고

### 부족수량

```
부족수량 = 필요수량 − (그 주문 차례에 남아 있던 가용재고 + 쓸 수 있는 입고예정 잔여)
```

같은 품목 · 창고의 부족분은 **주문을 가로질러 합산**한다. 주문마다 따로 내면 같은 품목
발주가 두 장 나가고, 둘 다 들어오면 재고가 남는다.

발주 대상이 아닌 것은 사유를 남긴다 — 미등록 품목 · 세트 · 서비스 · 기본공급처 없음 ·
중지 창고.

### 발주

| 품목유형 | 문서          | 진행                  |
| -------- | ------------- | --------------------- |
| 매입품   | 구매발주 (PO) | 발주 확정 → 입고      |
| 생산품   | 생산의뢰 (MO) | 진행 중 → 검사 → 입고 |

입고창고는 그 주문의 출고창고로 **고정**하고, 사용가능예정일은 기준시각 + 공급처 리드타임
으로 계산한다. 생성 폼(`/inbound/new`)이 문서구분과 창고를 드롭다운으로 열지 않는 이유다 —
규칙이 정한 값을 고르게 하면 담당자가 규칙을 깨는 선택을 할 수 있다.

**발주를 만들어도 현재고는 늘지 않는다.** 확정해야 판정에 쓰이고, 입고해야 현재고가 는다.

### 입고

```
구매발주   수량 확인 → 입고
생산의뢰   ① 품질검사 결과 기록 → ② 합격수량만 입고
```

검사 없이 입고하면 `INSPECTION_PENDING` 으로 막는다. **불합격 수량만큼 계획수량이
줄어든다** — 그대로 두면 잔여가 남아 담당자가 오지 않을 물량을 계속 기다린다.

시리얼 관리 품목은 입고 수량만큼 개체가 생긴다. 번호는 자동 채번하되 담당자가 고칠 수
있고(실물 라벨과 달라지면 이후 피킹에서 어느 개체를 집을지 알 수 없다), 중복이면 거부한다.

입고로 재고가 늘면 다음 판정에서 그 물량을 기다리던 주문이 자동으로 풀린다. 판정을
저장하지 않고 매번 계산하기 때문이다.

## 4. 중복 데이터와 반복 요청

### 중복 데이터

| 상황                                  | 처리                                                                                    |
| ------------------------------------- | --------------------------------------------------------------------------------------- |
| 같은 주문이 품목별 여러 행으로 온다   | `groupOrderRows` 로 주문 단위로 접는다                                                  |
| 일반 라인과 세트 구성품에 같은 품목   | 수요를 **합산**한다                                                                     |
| 04_재고현황의 `기존예약주문번호`      | 주문을 한 건만 적어 누적 예약을 나눌 수 없다 → 앱의 예약은 `Reservation` 으로 따로 추적 |
| 같은 품목 · 창고 부족분이 여러 주문에 | 합산해 문서 한 장으로 낸다                                                              |

### 반복 요청

재고를 바꾸는 모든 동작이 **요청 ID** 를 갖는다 (`domain/request/idempotency`).
이미 처리된 ID 면 `DUPLICATE_REQUEST` 로 막고 아무것도 바꾸지 않는다.

```
예약 · 출고    주문번호가 그대로 키다      RESERVE:ORD202607200016
입고 · 발주    화면이 토큰을 만든다        RECEIVE:PO-20260719-DMN:3
```

입고에는 자연 키가 없기 때문이다 — 계획 10개 문서에 3개를 두 번 넣으면 둘 다 정당한 부분
입고로 보인다. 토큰은 **성공한 뒤에만** 올라간다. 같은 버튼을 두 번 누르면 토큰이 같아
막히고, 담당자가 일부러 다시 입고하면 새 요청이 된다.

## 5. 예약 · 피킹 · 출고 · 입고의 숫자 정합성

### 재고가 움직이는 두 방향

| 행위                    | 현재고 | 예약수량 | 가용재고 | 개체상태                   |
| ----------------------- | ------ | -------- | -------- | -------------------------- |
| 예약 · 피킹             | –      | **+**    | **−**    | 창고 보관 중 → 주문 배정됨 |
| 출고                    | **−**  | **−**    | –        | 주문 배정됨 → 출고 완료    |
| 발주 생성 · 확정 · 검사 | –      | –        | –        | –                          |
| 입고 (합격분)           | **+**  | –        | **+**    | 신규 개체 생성             |

`가용재고 = 현재고 − 예약수량` 이므로 예약은 현재고를 건드리지 않는다.
**예약과 피킹이 현재고를 절대 바꾸지 않는다** — `tests/rules` 가 이 한 줄을 지킨다.

### 동시 요청과 중간 실패

백엔드가 없으므로 서버 개념을 인메모리 구조로 옮겼다.

| 서버 개념         | 이 프로젝트                                    |
| ----------------- | ---------------------------------------------- |
| 트랜잭션 경계     | 스토어 액션 하나 — `set()` 한 번에 전체 대입   |
| rollback          | 도메인 함수가 실패 시 **입력을 그대로 반환**   |
| 최신 상태 재확인  | 액션이 `get()` 으로 현재 상태를 다시 읽고 판정 |
| idempotency key   | `ProcessedRequest` 기록                        |
| unique constraint | 입고 시 시리얼번호 중복 검사                   |

**전량 아니면 전무.** 예약은 모든 품목과 개체를 확보해야 반영된다. 하나라도 모자라면
도메인 함수가 입력을 그대로 돌려주므로, 스토어가 분기 없이 대입해도 아무것도 바뀌지 않는다.
부분 반영이라는 상태 자체가 만들어지지 않는다.

**중간 상태를 만들지 않는다.** 재고 · 개체 · 예약을 따로 세 번 대입하면 그 사이에 렌더가
끼어 04_재고현황과 05_개체재고가 어긋난 화면이 보인다. 한 번에 대입한다.

**화면이 본 숫자를 믿지 않는다.** 목록을 띄워둔 사이 다른 주문이 예약을 잡았을 수 있으므로,
액션은 항상 최신 상태로 판정을 다시 세운다.

### 검산할 수 있게 보여준다

숫자를 나열하는 것으로는 "믿을 수 있나" 에 답이 되지 않는다. 제품 화면의 품목 서랍은 두
항등식을 값과 함께 보여주고, 어긋나면 등호가 `≠` 로 바뀐다.

```
가용재고  2  = 현재고 3 − 예약 1
현재고    3  = 보관 2 + 배정 1     ← 어긋나면 예약이 개체 부족으로 막히는 원인
```

세 화면 머리말에 `기준시각 2026.07.21 09:00 · 내 처리 12건` 을 둔다. 화면의 숫자는 엑셀
스냅샷과 담당자의 처리 결과 두 겹인데, 구분이 없으면 "내 조작이 반영된 건가" 에 답할 수
없다. 처리 직후에는 그 행에 `방금 입고` 를 남긴다.

## 6. 자동화 테스트

398개. 세 축으로 나뉜다.

| 축                 | 파일                                                                             | 무엇을 지키나                              |

| **규칙 하나씩**    | `tests/preparation/*` `tests/inventory/*` `tests/purchase/*` `tests/receiving/*` | 손으로 세운 최소 데이터로 규칙 하나만 확인 |

도메인 테스트는 시드를 쓰지 않는다. 29건이 얽힌 상태에서는 한 규칙만 확인할 수 없고, 시드
한 줄을 고치면 무관한 테스트가 깨진다. 반대로 골든 파일은 시드를 그대로 넣는다 — 앞선
주문이 가져간 몫, 접수시각 tie-break, 입고예정 선점이 얽힌 결과는 그렇게만 드러난다.

| 2   | 취소 품목과 취소 · 출고완료 · 배송완료 주문은 새 예약과 재고 변경을 만들지 않는다 | `preparation/cancelled` · `rules`                             |
| 3   | 현재고만으로 준비되는 주문과 검사 · 생산 · 구매입고 대기가 구분된다               | `preparation/statusLabel` · `golden`                          |
| 4   | 한 품목만 부족해도 다른 품목까지 일부 예약되지 않는다                             | `inventory/reserve` · `rules`                                 |
| 5   | 미등록 품목 · 중지 창고 · 잘못된 수량은 재고를 바꾸지 않고 사유가 표시된다        | `preparation/exception` · `ui/OrderDetailPage`                |
| 6   | 같은 예약 · 출고를 반복해도 중복 변경되지 않는다                                  | `inventory/reserve` · `inventory/ship` · `inventory/movement` |
| 7   | 매입품은 구매발주, 생산품은 생산의뢰로 나가고 입고 전에는 현재고가 늘지 않는다    | `purchase/order` · `flow`                                     |
| 8   | 같은 입고를 반복해도 한 번만 늘고, 계획수량 초과는 거부된다                       | `receiving/receive` · `rules`                                 |

7번 후반("입고 후 그 주문이 준비 가능으로 바뀐다")은 `flow` 가 한 바퀴로,
`ui/OrderDetailPage` 가 화면에서 각각 확인한다.

### 화면을 집는 방법

**접근성 이름(role + name)으로 집는다.** 버튼은 라벨로, 표는 `columnheader` 로, 영역은
`aria-label` 로 찾는다. 스크린리더가 읽는 것과 같은 것을 보므로, 마크업이 바뀌어도
사용자가 보는 것이 그대로면 통과한다. `data-testid` 는 그렇게 집을 수 없는 자리에만 쓰고
`tests/testIds.ts` 에 모은다.

## 7. 구조

```
src/
├── types/       엑셀 시트별 엔티티 타입 (선언만)
├── domain/      순수 비즈니스 규칙 (React · 스토어를 모른다)
├── data/        시드와 컬렉션 접근 계층
├── store/       zustand — 도메인 함수를 조립해 상태를 옮긴다
├── features/    업무 단위 표시용 타입과 유틸
├── components/  공통 UI (common) 와 앱 셸 (layout)
├── pages/       라우트가 가리키는 화면
├── styles/      토큰 · 시맨틱 테마 · 전역 스타일
└── tests/       도메인 · 스토어 · 화면 테스트
```

의존 방향은 한쪽으로만 흐른다.

```
app → pages → features → { components, store } → domain → data → types
```

**계산과 화면을 분리한다.** 페이지 `.tsx` 에는 재고 계산이 한 줄도 없다. 판정은 `domain/`
이, 표시용 가공은 `hooks.ts` 와 `features/*/utils.ts` 가 끝낸다. `domain/` 은 상위 계층을
모르는 순수 함수라 브라우저 없이 실행 · 검증할 수 있다.

## 8. 구현하지 못한 것과 확인이 필요한 위험

**필수 시나리오 8개는 모두 구현되어 있다.** 아래는 그 밖에서 손대지 못한 것들이다.

### 시간상 구현하지 못한 것

| 항목                                         | 대신                                                                        |
| -------------------------------------------- | --------------------------------------------------------------------------- |
| 부족분을 여러 주문에 걸쳐 묶어 발주하는 화면 | 같은 품목 · 창고 부족분은 자동 합산되지만, 묶음을 담당자가 조정할 수는 없다 |
| 피킹을 예약에서 분리 (개체 수동 선택)        | 예약이 개체 배정까지 한 트랜잭션. 배정 결과는 주문 상세에서 확인            |
| 입고 예정일 지연 알림                        | 목록에서 색으로만 표시                                                      |
| 엑셀 업로드 · 배송 완료 처리                 | 과제 제외 범위                                                              |

### 추가로 확인할 위험

- **저장분이 브라우저 하나에 갇힌다.** localStorage 는 사용자 · 브라우저별이라 담당자가
  여럿인 상황을 재현하지 못한다. 실제 운영이라면 서버 트랜잭션과 row lock 이 있어야 한다.
- **동시 요청은 한 탭 안에서만 안전하다.** 액션이 최신 상태를 다시 읽고 한 번에 대입하므로
  한 탭 안에서는 어긋나지 않지만, 같은 상태를 두 탭이 각자 저장하면 나중에 저장한 쪽이
  이긴다. 저장 시점의 버전을 비교하는 처리는 없다.
- **이력은 재고 칸의 변화만 남긴다.** 검사 통과 · 발주 확정처럼 재고를 움직이지 않는
  처리는 이력에 서지 않고 문서 상태로만 확인한다.
- **미확정 문서를 확정해도 시드에서는 어떤 주문의 상태도 뒤집히지 않는다.** 날짜 제약
  때문이다 — `PO-20260721-PIL` 은 07-23 도착이라 07-22 · 07-23 배송 주문이 쓸 수 없고
  (사용가능예정일 <= 배송일 − 1일), `PO-20260721-FRMK` 가 채우는 품목은 이미 준비 가능하다.
  확정은 그 물량을 입고예정으로 세어지게 만들 뿐이다 (`tests/purchase/confirm`).
- **화면은 jsdom 테스트로만 확인했다.** 실제 브라우저에서의 렌더 · 반응형 · 인쇄는 검증
  범위 밖이다.
