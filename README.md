# 재고 흐름 ERP

## 1. 프로젝트 소개

주문 데이터를 기준으로 **배송 예정 상품의 재고 수요를 계산**하고, 준비 가능 여부를 판정한 뒤
**예약 · 출고(재고 감소)** 또는 **발주 · 입고(재고 증가)** 까지 처리하는 ERP 화면입니다.

기준 시각은 **2026-07-21 09:00** 이며, 이 시점의 창고 스냅샷을 출발점으로 삼습니다.

백엔드 없이 동작하는 프론트엔드 단일 프로젝트입니다. 재고를 변경하는 규칙은 모두 순수
함수로 분리되어 있고, 자동화 테스트로 검증됩니다.

## 3. 화면 구성

화면은 담당자가 하루에 던지는 질문 순서대로 구성했습니다.

| 화면     | 답하는 질문                                              | 경로       |
| -------- | -------------------------------------------------------- | ---------- |
| **제품** | 지금 창고에 무엇이 얼마나 있고, 그 숫자를 믿을 수 있는가 | `/items`   |
| **주문** | 그 재고로 무엇을 내보낼 수 있고, 다음에 무엇을 하는가    | `/orders`  |
| **발주** | 모자란 것을 어떻게 채우고, 채워지면 무엇이 풀리는가      | `/inbound` |

상세 화면은 URL 에 반영되어 서로를 링크로 가리킬 수 있습니다.

```
/items/:itemKey       품목 상세 (품목:창고)
/orders/:orderId      주문 상세
/inbound/:documentId  입고 처리
/inbound/new          발주 생성
```

### 저장

처리 결과는 다시 실행해도 남아야 하므로 zustand `persist` 로 localStorage 에 저장합니다.

| 구분           | 대상                                                                                |
| -------------- | ----------------------------------------------------------------------------------- |
| **저장함**     | 재고 · 개체 · 주문 · 입고예정 문서 · 예약 · 출고 · 재고 이력 · **처리한 요청 기록** |
| **저장 안 함** | 품목 · 세트구성 · 창고 · 공급처 · 기준시각                                          |

- 기준정보는 매번 시드에서 다시 읽습니다. 저장해 두면 시드를 수정해도 예전 사본이 남습니다.
- **처리한 요청 기록을 함께 저장하는 것이 중요합니다.** 이 기록이 사라지면 새로고침 후 같은
  요청이 다시 통과해 재고가 두 번 차감됩니다.

## 5. 재고 수요 계산과 준비 가능 여부 판정

### 재고 수요 계산

주문 상품 중 **실제 재고가 필요한 상품만** 수요에 포함합니다.

| 주문 상품   | 처리                              |
| ----------- | --------------------------------- |
| 일반 상품   | 재고 수요에 포함                  |
| 세트 상품   | 구성품으로 전개하여 구성품을 포함 |
| 설치 서비스 | 재고 수요에서 제외                |
| 수거 서비스 | 재고 수요에서 제외                |
| 취소된 품목 | 재고 수요에서 제외                |

### 세트 전개

세트 상품 자체를 하나의 재고로 계산하지 않고 구성품 단위로 전개합니다.

```
Z10 + 데이먼 세트 Q  1개
  ↓
Z10 매트리스 Q    1개   → 재고 수요에 포함
데이먼 프레임 Q    1개   → 재고 수요에 포함
설치 서비스        1개   → 재고 수요에서 제외
```

- 세트 안에 세트가 있으면 **끝까지 재귀적으로** 전개합니다. 제공된 데이터에는 중첩 세트가
  없지만, 규칙으로 구현하고 테스트로 검증했습니다.
- 일반 주문 행과 세트 구성품에 같은 품목이 있으면 수량을 **합산**합니다.
- 전개 중 발견한 문제(미등록 품목, 순환 참조 세트, 구성품 없는 세트)는 버리지 않고 사유로
  남깁니다. 조용히 버리면 준비 가능한 주문처럼 보이기 때문입니다.

따라서 재고 부족 여부도 구성품 기준으로 판단합니다.

### 주문 상태

취소 · 출고 완료 · 배송 완료 주문은 새로 준비할 대상이 아니므로 판정에서 제외합니다.

- 제외된 주문은 목록에서 기본으로 숨기되, `제외 주문 포함` 토글로 확인할 수 있습니다.
- 이미 출고가 완료된 상품은 실제 물류 처리 이력이 남아 있으므로, 재고를 되돌리지 않고 이력
  그대로 조회됩니다.
- 제외된 주문에 예약이나 출고를 시도하면 거부하고 재고를 변경하지 않습니다.

### 준비 가능 여부 판정

주문을 하나씩 따로 판정하면 안 됩니다. 가용재고 1개를 두 주문이 각각 필요로 할 경우 둘 다
"준비 가능" 으로 표시되지만, 실제로 나가는 것은 한 건이기 때문입니다.

그래서 **배정 원장**을 한 번 만들고 배송일 순서대로 재고를 넘겨줍니다.

```
정렬 기준: 배송예정일 오름차순 → 주문접수일시 오름차순

각 주문마다
  1. 가용재고에서 먼저 차감하고, 모자라면 입고예정에서 당겨옵니다.   (계산만, 원장 미변경)
  2. 판정
       부족분이 있으면       → 재고 부족
       입고예정을 사용했으면 → 대기
       그 외                 → 바로 준비 가능
  3. 재고 부족이 아니면 원장에서 실제로 차감합니다.                  (반영)
```

**입고예정을 사용할 수 있는 조건** — 네 가지를 모두 만족해야 합니다.

- 확정된 문서일 것 (확정여부 = 예)
- 사용 중인 창고이고, 주문의 출고창고와 일치할 것
- 사용가능예정일 ≤ 배송예정일 − 1일
- 잔여수량(계획 − 입고) > 0

### 준비상태 구분

화면에서는 6가지로 구분합니다.

```
바로 준비 가능
품질검사 대기
생산 완료 대기
구매 입고 대기
재고 부족
확인 필요
```

내부 코드는 대기 3종을 하나로 들고 사유를 붙여 관리합니다. 판정 로직에서 셋의 취급이 같기
때문입니다. 다만 화면에서는 나누어 보여줍니다. '입고 대기' 한 마디로 묶으면 담당자가 언제
풀릴지 가늠할 수 없기 때문입니다. 사유가 겹칠 때는 **가장 오래 걸리는 단계**를 대표로
표시합니다.

### 재고 부족 주문은 재고를 선점하지 않습니다

"일부 품목만 가능하다면 그 주문의 일부 수량을 먼저 잡아두지 않는다" 는 규칙을 예약뿐 아니라
**판정 단계에도** 적용했습니다.

부족한 주문이 재고 절반을 붙잡으면, 그 재고로 전량 준비할 수 있었던 뒤 주문까지 함께 막히기
때문입니다. 대신 배송일이 늦은 주문이 먼저 가져갈 수 있다는 점은 감수했습니다.

이 결정 때문에 배정 함수를 **계산(simulate)** 과 **반영(commit)** 으로 나누었습니다. 판정을
마쳐야 그 주문이 부족한지 알 수 있어, 계산과 반영을 같은 함수에서 처리할 수 없습니다.

> 이 규칙을 빠뜨렸을 때 `ORD202607200027` 이 재고 부족으로 잘못 판정되었고, 골든 파일
> 테스트가 그 한 건을 찾아냈습니다.

## 6. 부족수량 계산과 발주 · 입고

### 부족수량

```
부족수량 = 필요수량 − (해당 주문 차례에 남아 있던 가용재고 + 사용 가능한 입고예정 잔여)
```

같은 품목 · 창고의 부족분은 **여러 주문에 걸쳐 합산**합니다. 주문마다 따로 발주하면 같은
품목 발주가 두 건 나가고, 둘 다 입고되면 재고가 남기 때문입니다.

발주 대상이 아닌 경우(미등록 품목, 세트, 서비스, 기본공급처 없음, 사용 중지 창고)는 발주하지
않고 사유를 남깁니다.

### 발주

품목유형에 따라 문서가 나뉩니다.

| 품목유형 | 문서          | 진행                  |
| -------- | ------------- | --------------------- |
| 매입품   | 구매발주 (PO) | 발주 확정 → 입고      |
| 생산품   | 생산의뢰 (MO) | 진행 중 → 검사 → 입고 |

- 입고창고는 해당 주문의 출고창고로 고정됩니다.
- 사용가능예정일은 기준시각 + 공급처 리드타임으로 계산됩니다.
- **발주를 생성해도 현재고는 늘지 않습니다.** 확정해야 판정에 반영되고, 입고해야 현재고가
  증가합니다.

발주 생성 화면(`/inbound/new`)에서 담당자가 입력하는 것은 **수량 · 공급처 · 사용가능예정일**
세 가지뿐입니다. 문서구분과 입고창고는 규칙이 정하는 값이라, 선택하게 두면 규칙을 어기는
입력이 가능해집니다.

### 입고

```
구매발주   수량 확인 → 입고
생산의뢰   ① 품질검사 결과 기록 → ② 합격수량만 입고
```

- 검사를 기록하지 않고 입고하면 거부합니다.
- **불합격 수량만큼 계획수량이 줄어듭니다.** 그대로 두면 잔여가 남아 담당자가 오지 않을
  물량을 계속 기다리게 됩니다.
- 시리얼 관리 품목은 입고 수량만큼 개체가 생성됩니다. 번호는 자동으로 채번하되 담당자가
  수정할 수 있고, 중복이면 거부합니다.
- 계획수량 또는 잔여수량을 초과하는 입고는 거부합니다.

입고로 재고가 늘면 다음 판정에서 그 물량을 기다리던 주문이 자동으로 풀립니다. 판정 결과를
저장하지 않고 매번 다시 계산하기 때문입니다.

## 7. 중복 데이터와 반복 요청 처리

### 중복 데이터

| 상황                                  | 처리                                                                     |
| ------------------------------------- | ------------------------------------------------------------------------ |
| 하나의 주문이 품목별 여러 행으로 존재 | 주문 단위로 묶습니다                                                     |
| 일반 행과 세트 구성품에 같은 품목     | 수량을 합산합니다                                                        |
| 재고현황의 `기존예약주문번호`         | 주문 한 건만 기록되어 누적 예약을 나눌 수 없어, 예약을 별도로 추적합니다 |
| 같은 품목 · 창고 부족분이 여러 주문에 | 합산하여 문서 한 건으로 발주합니다                                       |

### 반복 요청

재고를 변경하는 모든 동작에 **요청 ID** 를 부여했습니다. 이미 처리한 ID 면 거부하고 아무것도
변경하지 않습니다.

| 동작        | 요청 ID                | 예시                        |
| ----------- | ---------------------- | --------------------------- |
| 예약 · 출고 | 주문번호를 그대로 사용 | `RESERVE:ORD202607200016`   |
| 입고 · 발주 | 화면이 토큰을 생성     | `RECEIVE:PO-20260719-DMN:3` |

입고에는 자연 키가 없기 때문입니다. 계획 10개인 문서에 3개를 두 번 입고하면 둘 다 정당한
부분 입고로 보입니다.

토큰은 **성공한 뒤에만** 증가합니다. 따라서 같은 버튼을 두 번 누르면 토큰이 같아 차단되고,
담당자가 의도적으로 다시 입고하면 새 요청으로 처리됩니다.

## 8. 예약 · 피킹 · 출고 · 입고의 숫자 정합성

### 재고가 움직이는 방향

| 행위                    | 현재고   | 예약수량 | 가용재고 | 개체상태                   |
| ----------------------- | -------- | -------- | -------- | -------------------------- |
| 예약 · 피킹             | –        | **증가** | **감소** | 창고 보관 중 → 주문 배정됨 |
| 출고                    | **감소** | **감소** | –        | 주문 배정됨 → 출고 완료    |
| 발주 생성 · 확정 · 검사 | –        | –        | –        | –                          |
| 입고 (합격분)           | **증가** | –        | **증가** | 신규 개체 생성             |

`가용재고 = 현재고 − 예약수량` 이므로 **예약과 피킹은 현재고를 변경하지 않습니다.**

### 동시 요청과 중간 실패

백엔드가 없으므로 서버의 개념을 인메모리 구조로 옮겼습니다.

| 서버 개념        | 이 프로젝트                                         |
| ---------------- | --------------------------------------------------- |
| 트랜잭션 경계    | 스토어 액션 하나 — 상태를 한 번에 통째로 반영합니다 |
| 롤백             | 도메인 함수가 실패하면 **입력을 그대로 반환**합니다 |
| 최신 상태 재확인 | 액션이 현재 상태를 다시 읽고 판정합니다             |
| 멱등성 키        | 처리한 요청 기록                                    |
| 유니크 제약      | 입고 시 시리얼번호 중복 검사                        |

**전량 아니면 전무로 처리합니다.**
예약은 모든 품목과 개체를 확보해야 반영됩니다. 하나라도 모자라면 도메인 함수가 입력을 그대로
반환하므로, 스토어가 분기 없이 반영해도 아무것도 바뀌지 않습니다. 부분 반영이라는 상태 자체가
만들어지지 않습니다.

**중간 상태를 만들지 않습니다.**
재고 · 개체 · 예약을 따로 세 번 반영하면 그 사이에 화면이 다시 그려져, 재고현황과 개체재고가
어긋난 상태가 보일 수 있습니다. 한 번에 반영합니다.

**화면이 읽은 숫자를 신뢰하지 않습니다.**
목록을 띄워둔 사이 다른 주문이 예약을 잡았을 수 있으므로, 액션은 항상 최신 상태로 판정을 다시
세웁니다.

### 검산할 수 있게 보여줍니다

품목 상세에서 두 항등식을 값과 함께 보여주고, 어긋나면 등호가 `≠` 로 바뀝니다.

```
가용재고  2  =  현재고 3 − 예약 1
현재고    3  =  보관 2 + 배정 1
```

두 번째가 어긋나면 수량이 맞아 보여도 예약이 개체 부족으로 막히는 원인이 됩니다.

또한 세 화면 머리말에 `기준시각 2026.07.21 09:00 · 내 처리 12건` 을 표시합니다. 화면의 숫자는
엑셀 스냅샷과 담당자의 처리 결과가 겹쳐 있어, 구분이 없으면 "내 조작이 반영된 것인가" 에 답할
수 없기 때문입니다.

## 9. 자동화 테스트

테스트가 있다는 것보다 **업무 규칙을 검증한다**는 점을 기준으로 구성했습니다. 테스트 이름을
그대로 읽으면 이 시스템의 규칙 목록이 되도록 작성했습니다.

총 **401개** 이며, 이 중 **255개가 업무 규칙 검증**이고 146개가 화면 테스트입니다.

| 축            | 검증 대상                                              |
| ------------- | ------------------------------------------------------ |
| **업무 규칙** | 재고 수요 계산 · 준비 판정 · 예약 · 출고 · 발주 · 입고 |
| **골든 파일** | 주문 29건의 기대 판정값과 배정 후 잔량을 대조합니다    |
| **화면**      | 규칙이 화면에 올바르게 드러나는지 확인합니다           |

업무 규칙 테스트는 시드를 사용하지 않고 최소 데이터를 직접 구성합니다. 29건이 얽힌 상태에서는
규칙 하나만 확인할 수 없고, 시드 한 줄을 고치면 무관한 테스트가 깨지기 때문입니다.

### 검증하는 업무 규칙

**재고 수요 계산**

```
✓ 일반 상품은 주문 수량만큼 재고 수요에 포함된다
✓ 세트 1개는 구성품 수량으로 풀린다
✓ 세트 수량만큼 구성품 수량이 곱해진다
✓ 세트상품 자체는 준비 품목으로 남지 않는다
✓ 세트 안의 세트도 끝까지 풀린다
✓ 세트에 묶인 설치 서비스는 재고 수요에서 빠진다
✓ 수거 서비스는 재고 수요에서 제외된다
✓ 주문행으로 직접 들어온 서비스도 제외된다
✓ 일반 주문행과 세트 구성품의 같은 품목은 합산된다
```

**취소 데이터**

```
✓ 취소 품목은 수요에서 빠지고 정상 품목만 남는다
✓ 정상 품목이 하나도 없으면 준비할 것이 없다
✓ 주문상태가 '취소' 면 준비 대상이 아니다
✓ 주문상태가 '출고 완료' 면 준비 대상이 아니다
✓ 주문상태가 '배송 완료' 면 준비 대상이 아니다
✓ 취소 주문은 배송일이 빨라도 재고를 잡지 않는다
```

**준비 상태 판정**

```
✓ 가용재고로 전량 채우면 바로 준비 가능이다
✓ 가용재고는 현재고에서 예약수량을 뺀 값이다
✓ 다른 창고의 재고는 합산하지 않는다
✓ 배송일 전에 도착하는 확정 발주가 채우면 대기다
✓ 입고예정까지 더해도 모자라면 재고 부족이다
✓ 확정여부가 '아니오' 인 문서는 세지 않는다
✓ 부분 입고분은 현재고와 입고예정에 이중으로 세지 않는다
✓ 배송일 07/25 기준, 도착 07/24 는 대기 · 07/25 는 재고 부족   [배송일 − 1일 경계]
✓ 생산 중이면 생산 완료를, 검사가 남았으면 품질검사를 기다린다
✓ 주문 상태는 품목 중 가장 나쁜 것을 따른다
```

**재고 변경 — 절대 규칙**

```
✓ 예약하면 예약수량만 늘고 현재고는 그대로다
✓ 예약하면 개체가 주문에 배정된다
✓ 출고 후 현재고와 예약수량이 같은 양만큼 내려간다
✓ 한 품목이라도 부족하면 아무것도 예약되지 않는다
✓ 취소 · 출고 완료 · 배송 완료 주문은 예약할 수 없다
✓ 이미 출고된 주문의 재고와 개체 이력은 되돌리지 않는다
✓ 같은 품목이 다른 창고에 있어도 부족은 부족이다
```

**발주와 입고**

```
✓ 발주 생성 후 현재고가 그대로다
✓ 입고 처리를 해야 현재고가 는다
✓ 검사 전에는 입고를 거부한다
✓ 검사를 통과해야 입고할 수 있다
✓ 계획수량을 넘는 입고는 거부된다
✓ 사용 중지 창고 주문은 확인 필요이고 재고를 바꾸지 않는다
✓ 미확정 발주는 부족 판정을 뒤집지 못한다
```

**반복 요청**

```
✓ 같은 예약을 두 번 보내도 재고가 한 번만 바뀐다
✓ 같은 입고 요청을 두 번 보내도 입고수량이 한 번만 는다
✓ 같은 요청을 반복해도 이력이 두 줄 쌓이지 않는다
```

### 과제 필수 시나리오 대조

| #   | 시나리오                                                                      | 테스트                                                        |
| --- | ----------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 1   | 세트 상품이 구성품으로 전개되고 설치 · 수거 서비스가 제외되는지               | `preparation/demand`                                          |

### 화면 테스트

화면 테스트는 버튼이 눌리는지가 아니라 **규칙이 화면에 올바르게 드러나는지**를 확인합니다.

- 재고 부족 주문에 예약 버튼이 나오지 않는지
- 확인 필요 주문에 사유만 있고 액션이 없는지
- 잔여를 넘는 입고에서 처리 버튼이 막히는지
- 입고 후 현재고가 늘고 잔여가 줄어드는지

요소는 **접근성 이름(role + name)** 으로 찾습니다. 스크린리더가 읽는 것과 같은 것을 보므로,
마크업이 바뀌어도 사용자가 보는 결과가 같으면 통과합니다. `data-testid` 는 그렇게 찾을 수 없는
자리에만 사용하고 `tests/testIds.ts` 에 모아 두었습니다.

## 10. 주요 설계 기준

화면에서 단순히 데이터를 표시하는 것보다, 실제 ERP 업무 흐름을 기준으로 재고 계산 로직을
분리하여 구현했습니다.

```
주문 데이터
  → 세트 전개 · 서비스 제외
  → 재고 수요 계산
  → 현재 재고 · 입고예정과 비교
  → 준비 가능 여부 판정
  → 예약 · 출고  또는  발주 · 입고
```

### 계층 구조

```
src/
├── types/       엑셀 시트별 엔티티 타입
├── domain/      순수 비즈니스 규칙 (React · 스토어를 모릅니다)
├── data/        시드와 데이터 접근 계층
├── store/       zustand — 도메인 함수를 조립해 상태를 변경합니다
├── features/    업무 단위 표시용 타입과 유틸
├── components/  공통 UI 와 앱 레이아웃
├── pages/       라우트가 가리키는 화면
├── styles/      토큰 · 테마 · 전역 스타일
└── tests/       도메인 · 스토어 · 화면 테스트
```

의존 방향은 한쪽으로만 흐릅니다.

```
app → pages → features → { components, store } → domain → data → types
```

### 계산과 화면의 분리

- 페이지 컴포넌트에는 재고 계산이 한 줄도 없습니다.
- 판정은 `domain/` 이, 표시용 가공은 `hooks.ts` 와 `features/*/utils.ts` 가 담당합니다.
- `domain/` 은 상위 계층을 모르는 순수 함수이므로 브라우저 없이 실행하고 검증할 수 있습니다.

## 11. 구현하지 못한 점과 확인이 필요한 위험

### 시간상 구현하지 못한 점

| 항목                                         | 현재 상태                                                              |
| -------------------------------------------- | ---------------------------------------------------------------------- |
| 부족분을 여러 주문에 걸쳐 묶어 발주하는 화면 | 자동으로 합산되지만 담당자가 묶음을 조정할 수는 없습니다               |
| 피킹을 예약에서 분리 (개체 수동 선택)        | 예약이 개체 배정까지 한 번에 처리하며, 결과는 주문 상세에서 확인합니다 |
| 입고 예정일 지연 알림                        | 목록에서 색으로만 표시합니다                                           |
| 엑셀 업로드 · 배송 완료 처리                 | 과제 제외 범위입니다                                                   |

### 추가로 확인할 위험

- **저장 결과가 브라우저 하나에 한정됩니다.**
  localStorage 는 사용자 · 브라우저별이라 담당자가 여럿인 상황을 재현하지 못합니다. 실제
  운영이라면 서버 트랜잭션과 행 잠금이 필요한 자리입니다.

- **동시 요청은 하나의 탭 안에서만 안전합니다.**
  액션이 최신 상태를 다시 읽고 한 번에 반영하므로 한 탭 안에서는 어긋나지 않지만, 같은
  상태를 두 탭이 각각 저장하면 나중에 저장한 쪽이 남습니다. 저장 시점의 버전을 비교하는
  처리는 없습니다.

- **이력은 재고 수량의 변화만 남깁니다.**
  검사 통과나 발주 확정처럼 재고를 움직이지 않는 처리는 이력에 남지 않고 문서 상태로만
  확인합니다.

- **미확정 문서를 확정해도 시드 데이터에서는 주문 상태가 뒤집히지 않습니다.**
  날짜 제약 때문입니다. `PO-20260721-PIL` 은 07-23 도착이라 07-22 · 07-23 배송 주문이 사용할
  수 없고(사용가능예정일 ≤ 배송일 − 1일), `PO-20260721-FRMK` 가 채우는 품목은 이미 준비
  가능한 상태입니다. 확정은 그 물량을 입고예정으로 계산되게 만드는 역할까지입니다.

- **화면은 jsdom 테스트로만 확인했습니다.**
  실제 브라우저에서의 렌더링과 반응형은 검증 범위 밖입니다.
