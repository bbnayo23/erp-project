# 재고 흐름 ERP

기준 시각 **2026-07-21 09:00** 의 창고 스냅샷에서, 확정된 주문을 배송일 순으로 훑어
**세트 전개 → 준비 가능 여부 판정 → 예약 · 피킹 · 출고(재고 감소)** 하거나
**부족분 발주 · 입고(재고 증가)** 하는 흐름을 세 화면으로 운영한다.

백엔드 없이 도는 프론트엔드 단일 프로젝트다. 재고를 바꾸는 모든 규칙이 순수 함수로 있고
`pnpm test` 로 검증된다.

```bash

pnpm typecheck
pnpm lint
pnpm build
pnpm verify:seed  # 엑셀 원본 ↔ 시드 셀 단위 대조 (Python 3)
```

## 이 솔루션이 답하는 질문

물류 담당자가 하루에 던지는 질문은 정해져 있다. 화면 셋은 그 순서다.

| 화면     | 답하는 질문                                            | 경로       |
| -------- | ------------------------------------------------------ | ---------- |
| **제품** | 지금 창고에 무엇이 얼마나 있고, 그 숫자를 믿을 수 있나 | `/items`   |
| **주문** | 그 재고로 무엇을 내보낼 수 있고, 다음에 뭘 하나        | `/orders`  |
| **발주** | 모자란 것을 어떻게 채우고, 채워지면 무엇이 풀리나      | `/inbound` |

**첫 화면은 제품이다.** 주문 화면의 준비상태도, 발주 화면의 부족수량도 전부 창고 재고에서
나온 결과다. 결과부터 보여주면 담당자는 그 숫자를 믿을 근거를 화면에서 찾지 못한다.

### 대시보드가 아니라 작업 대기열이다

한때 화면 위쪽에 `38%` 같은 비율을 얹은 지표 카드가 있었다. 걷어냈다.

대시보드는 "우리가 어떻게 하고 있나" 에 답하는 형식인데, 이 앱이 답해야 하는 것은
**"지금 이 숫자가 맞나, 그래서 뭘 하나"** 다. '재고 부족이 전체의 31%' 는 아무 행동도
유발하지 않는다. 담당자에게 의미 있는 것은 `8건 발주 필요` 뿐이다.

그래서 상단 카드는 지표가 아니라 **대기열 선택기**다. 라벨을 다음 행동으로 쓰고, 누르면
그 대기열만 남는다.

```
예약할 수 있음                    발주 필요
10건                             8건
가용재고로 전량 준비됩니다          입고예정까지 봐도 모자랍니다
→ 예약할 주문 보기                 → 부족한 주문 보기
```

### "이 숫자가 최신인가" 에 답하는 장치

화면의 숫자는 두 겹이다 — 엑셀에서 온 기준시각 스냅샷과, 담당자가 이 화면에서 처리해
그 위에 얹힌 결과. 섞여 있는데 구분이 없으면 "지금 이 재고가 내 조작을 반영한 것인가" 에
화면이 답하지 못한다.

- **세 화면 머리말에 같은 줄**을 둔다: `기준시각 2026.07.21 09:00 · 내 처리 12건 · 마지막 입고 …`
- 예약 · 출고 · 입고 직후 그 처리가 건드린 행에 **`방금 입고`** 를 남긴다. 숫자만 바뀌면
  26줄 중 어디가 바뀐 것인지 다시 찾아야 한다.
- 둘 다 이미 있는 재고 변동 이력(`stockMovements`)에서 나온다.

### 검산 가능성을 표면으로

제품 화면의 본질은 "믿을 수 있나" 다. 숫자를 나열하는 것으로는 답이 되지 않고, 숫자끼리
맞아떨어지는 것을 보여줘야 한다. 품목 서랍 맨 위에 두 항등식을 둔다.

```
가용재고  2   = 현재고 3 − 예약 1
현재고    3   = 보관 2 + 배정 1
```

두 번째가 어긋나면 등호가 `≠` 로 바뀌고 붉게 선다. 04_재고현황과 05_개체재고가 어긋난
상태이고, 수량이 맞아 보여도 예약이 개체 부족으로 막히는 원인이다.

## 재고가 움직이는 두 방향

이 프로젝트에서 가장 중요한 불변식이다.

```
                  ┌───────────── 재고 감소 ─────────────┐
주문 확정 → 세트 전개 → 판정 → 예약 → 시리얼 피킹 → 출고
                            │      (수량 변화 없음)     (현재고↓ 예약수량↓)
                            │
                            └─ 재고 부족 → 발주 생성 → 입고(생산은 검사 통과 후) → 재판정
                                        (수량 변화 없음)     (현재고↑)
```

| 행위               | 현재고 | 예약수량 | 가용재고 | 개체상태                   |
| ------------------ | ------ | -------- | -------- | -------------------------- |
| 예약               | –      | **+**    | **−**    | 창고 보관 중 → 주문 배정됨 |
| 출고               | **−**  | **−**    | –        | 주문 배정됨 → 출고 완료    |
| 발주 생성          | –      | –        | –        | –                          |
| 입고 (검사 통과분) | **+**  | –        | **+**    | 신규 개체 생성             |

`가용재고 = 현재고 − 예약수량` 이므로 예약은 현재고를 건드리지 않는다.
**예약과 피킹이 현재고를 절대 바꾸지 않는다** — 이 한 줄을 `tests/rules` 가 지킨다.

## 화면별 핵심 로직

### 제품 `/items`

품목 × 창고 한 줄. 04_재고현황에 행이 없어도 **확정된 입고예정이 있으면 한 줄을 세운다** —
아직 그 창고에 없는 품목을 발주하면 입고 전까지 재고 행이 생기지 않는데, 그때 화면이
비어 있으면 담당자는 발주가 사라진 줄 안다.

**사용 중지 창고 재고를 숨기지 않는다.** WH-LEGACY 에는 재고와 개체가 남아 있고, 그것이
창고 합계와 출고 가능 수량이 어긋나는 이유다. 배지로 구분하되 지우지 않는다.

행을 누르면 품목 서랍이 열린다 — 항등식 · 개체 목록 · 이 품목을 기다리는 주문 · 걸려 있는
문서 · 재고 이력. 재고 숫자 하나를 보고 담당자가 이어서 묻는 것을 한자리에 모았다.

### 주문 `/orders`

**목록 순서가 곧 재고를 배정받은 순서다.** 배송일이 빠른 주문이 먼저 가져가고 남은 만큼만
뒤 주문에 간다. 그래서 순위를 첫 칸에 둔다 — 같은 품목을 원하는 두 주문의 상태가 다른
이유가 이 순서다.

상세는 좌우 두 칸이다. 왼쪽 레일이 배정 순서를 그대로 들고 있어, 상세로 들어와도 '내가
몇 번째를 보고 있는지' 와 '다음에 볼 주문' 을 잃지 않는다.

**처리 단계**가 다음 행동을 하나로 좁힌다.

```
~~부족분 발주~~ → ~~입고~~ → [예약] → 출고
┌──────────────────────────────────────┐
│ 다음 할 일 — 예약           [ 예약 ] │   ← 화면에서 유일하게 어두운 면
│ 재고와 개체를 이 주문에 묶습니다.      │
└──────────────────────────────────────┘
```

재고로 바로 채워지는 주문의 발주 · 입고 칸은 '대기' 가 아니라 '해당 없음' 이다. 할 일이
남은 것처럼 보이면 담당자가 있지도 않은 발주를 찾는다.

### 발주 `/inbound`

07_입고예정 문서 전체. 제공된 문서와 앱이 만든 문서가 같은 목록에 선다.

진행상태 7가지를 그대로 늘어놓지 않는다. `생산 완료` 와 `검사 완료` 는 서로 다른
진행상태지만 눌러야 하는 버튼이 각각 검사와 입고로 갈린다. **다음 행동으로 묶은 단계**를
따로 두고, 원본 진행상태 · 검사상태 · 확정여부는 옆 칸에 그대로 남긴다 — 담당자가 단계
판정을 검산할 수 있어야 한다.

입고 이력이 `+4 · 입고 후 현재고 10 · ORD…0012 바로 준비 가능` 을 남긴다. 문서 목록의
'입고수량' 은 누적 합계라 이번에 얼마가 들어왔는지도, 어느 주문이 풀렸는지도 말하지 않는다.

## 설계 결정

### 재고 부족 주문은 재고를 선점하지 않는다

`재고 부족` 판정을 받은 주문은 배정 원장을 소진하지 않는다.

근거는 "일부 품목만 가능하다면 그 주문의 일부 수량을 먼저 잡아두지 않습니다" 다. 이 규칙은
예약뿐 아니라 **판정에도** 적용된다. 부족한 주문이 절반을 붙잡으면, 그 재고로 전량 준비할
수 있었던 뒤 주문까지 함께 막힌다 — 나가지도 못할 주문이 나갈 수 있는 주문을 막는 셈이다.

대가는 배송일이 늦은 주문이 먼저 가져갈 수 있다는 것이다. 의도된 맞바꿈이다.

이 결정 때문에 `allocate` 를 `simulate` + `commit` 둘로 나눴다. 판정을 마쳐야 그 주문이
부족한지 알 수 있으니 계산과 반영을 같은 함수에서 할 수 없다.

> 실제로 이 규칙을 빠뜨려 `ORD202607200027` 이 `재고 부족` 으로 잘못 나왔다.
> 골든 파일 테스트가 그 한 건을 짚어냈다.

### 준비상태는 화면에서 6종, 코드에서 4종

내부 코드는 `WAITING` 하나에 사유를 붙여 들고 있다 — 판정 로직에서 셋의 취급이 같기
때문이다. 그러나 화면 문구는 `품질검사 대기` · `생산 완료 대기` · `구매 입고 대기` 로
갈린다. '입고 대기' 한 마디로 뭉치면 담당자가 언제 풀릴지 가늠할 수 없다.

여러 사유가 겹치면 **가장 오래 걸리는 단계**를 대표로 보여준다. 그 단계가 풀려야 주문이
나가기 때문이다.

### 준비상태와 처리단계는 독립된 두 축

`재고 부족 + 미착수`, `바로 준비 가능 + 예약 완료` 같은 조합이 존재한다. 한 컬럼에 섞지
않는다.

### 예약한 주문은 배정 경쟁에서 빠진다

예약수량은 이미 다른 주문의 가용재고에서 빠져 있다. 그 주문을 다시 원장에 넣으면 자기
예약 때문에 자기가 부족해진다 — 현재고 5 중 3을 예약하면 가용은 2 인데 소요는 여전히 3
이라 `재고 부족` 이 되고, 있는 재고를 두고 발주가 나간다.

## 정합성을 지킨 방법

백엔드가 없으므로 서버 개념을 인메모리 구조로 옮겼다.

| 서버 개념         | 이 프로젝트                                            |
| ----------------- | ------------------------------------------------------ |
| 트랜잭션 경계     | 스토어 액션 하나 — `set()` 한 번에 전체 대입           |
| rollback          | 도메인 함수가 실패 시 입력을 그대로 반환               |
| 최신 상태 재확인  | 액션이 `get()` 으로 현재 상태를 다시 읽고 판정         |
| idempotency key   | `ProcessedRequest` 기록 (`domain/request/idempotency`) |
| unique constraint | 입고 시 시리얼번호 중복 검사                           |
| 영속화            | `persist` — 앱이 바꾸는 컬렉션만 localStorage          |

**액션 하나가 트랜잭션 경계다.** 도메인 함수가 돌려준 컬렉션을 `set()` 한 번에 통째로
대입한다 — 재고와 개체를 따로 두 번 대입하면 그 사이에 렌더가 끼어 04_재고현황과
05_개체재고가 어긋난 중간 상태가 화면에 보인다.

**반복 요청.** 예약 · 출고는 주문번호가 그대로 멱등성 키가 된다(`RESERVE:ORD-001`).
입고 · 발주는 여러 번 일어날 수 있어 화면이 요청 토큰을 만든다 — 성공한 뒤에만 올라가므로,
같은 버튼을 두 번 누르면 토큰이 같아 막히고 담당자가 일부러 다시 입고하면 새 요청이 된다.

**저장.** 앱이 바꾸는 컬렉션만 저장한다. 기준정보(품목 · 세트구성 · 창고 · 공급처)와
기준시각은 시드에서 다시 읽는다 — 저장해 두면 시드를 고쳐도 옛 사본이 살아남는다.
`processedRequests` 를 함께 저장하는 것이 핵심이다. 이 기록이 사라지면 새로고침 뒤 같은
요청이 다시 통과해 재고가 두 번 깎인다.

### 골든 파일

`60-test-scenarios.md` 의 표를 그대로 옮겼다. 시드에 규칙을 손으로 적용해 계산한 값이라
이 표와 다르면 구현이 틀린 것이다. 29건이 서로 물린 상태 — 앞선 주문이 가져간 몫, 접수시각
tie-break, 입고예정 선점 — 는 이렇게만 드러난다.

### 화면을 집는 방법

**먼저 접근성 이름(role + name)으로 집는다.** 버튼은 라벨로, 표는 `columnheader` 로,
영역은 `aria-label` 로 찾는다. 그렇게 쓴 테스트는 스크린리더가 읽는 것과 같은 것을 보므로,
마크업이 바뀌어도 사용자가 보는 것이 그대로면 통과한다.

`data-testid` 는 그렇게 집을 수 없는 자리에만 쓰고 `tests/testIds.ts` 에 모은다.

- 접근 가능한 이름이 없는 것 — `방금 처리됨` 배지
- 같은 문구가 여러 번 나와 이름으로 특정되지 않는 것 — 항등식 줄

### 스타일 규칙도 테스트가 지킨다

## 구조

```
src/
├── types/       엑셀 시트별 엔티티 타입 (단일 출처, 선언만)
├── domain/      순수 비즈니스 규칙 (React·스토어를 모른다)
├── data/        시드 (seed) 와 컬렉션 접근 계층 (repositories)
├── store/       zustand — 도메인 함수를 조립해 상태를 옮긴다
├── features/    업무 단위 묶음 — 표시용 타입과 유틸
├── components/  화면에 종속되지 않는 UI (common) 와 앱 셸 (layout)
├── pages/       라우트가 가리키는 화면
├── styles/      토큰 · 시맨틱 테마 · 전역 스타일
└── tests/       도메인 · 스토어 · 화면 테스트
```

의존 방향은 한쪽으로만 흐른다.

```
app → pages → features → { components, store } → domain → data → types
```

`domain/` 은 어떤 상위 계층도 모른다. 순수 함수라 브라우저 없이 실행 · 검증할 수 있다.
`types/` 는 선언만 담는다 — 규칙(가용재고 계산, 창고 사용 여부, 입고 잔여수량)은 전부
`domain/` 에 둔다.

**계산과 화면을 분리한다.** 페이지 `.tsx` 에는 재고 계산이 한 줄도 없다. 판정은 도메인이,
표시용 가공은 `hooks.ts` 와 `features/*/utils.ts` 가 끝낸다.

## 디자인 규칙

|           |                                                                         |
| --------- | ----------------------------------------------------------------------- |
| 본문      | 12px — 한 화면에 몇 줄이 들어가느냐가 곧 사용성                         |
| 표 셀     | 세로 6px · 가로 10px, 한 줄 행 약 29px                                  |
| 카드      | 페이지에서 홀로 서는 구획만. 카드 안 구획은 선으로 나눈다               |
| 어두운 면 | 화면에 한 곳 — 지금 일하는 자리                                         |
| 포인트 색 | 로고 밑선 · 지금 처리할 지표 · 어두운 면의 주 액션, 셋뿐                |
| 움직임    | `transform` · `opacity` 만. `prefers-reduced-motion` 에서 전역으로 끈다 |

**세로 기준선이 하나다.** 구획 제목과 표의 첫 글자가 같은 선(`tableCell.paddingX`)에서
시작한다. 어긋나면 화면 전체가 삐뚤어 보인다.

**표의 고정 머리 줄은 `box-shadow: inset` 으로 선을 그린다.** `border-collapse: collapse`
에서 테두리는 셀이 아니라 표의 것이 되어, 머리 줄이 떠 있는 동안 스크롤에 밀려 사라진다.

## 명세 대비 미구현

화면 명세 중 아직 반영하지 않은 것.

| 항목                                                           | 상태                                            |
| -------------------------------------------------------------- | ----------------------------------------------- |
| 배송일별 그룹 헤더 (`── 2026-07-22 (수) · 6건 ──`)             | 미구현. 배송일 필터로 대신한다                  |
| `제외 주문 포함` 토글 (취소 · 출고완료 · 배송완료)             | 미구현. 목록에 아예 오르지 않는다               |
| 발주 생성 폼 `/inbound/new` (프리필 · 공급처 선택 · 즉시 확정) | 미구현. 주문 상세에서 부족분을 한 번에 발주한다 |
| 미확정 문서 `[확정]` 처리                                      | 미구현. 미확정으로 표시만 하고 판정에서 뺀다    |
| 입고 시 시리얼번호 편집                                        | 미구현. 자동 채번만 한다                        |
| 품질검사 불합격 수량 처리                                      | 미구현. 전량 합격만 지원한다                    |
| 상세를 URL 에 반영 (`/items/:itemCode` · `/inbound/:docNo`)    | 주문만 딥링크가 있다. 제품 · 발주는 서랍/인라인 |
| 엑셀 업로드 · 배송 완료 처리                                   | 과제 제외 범위                                  |

## 확인이 필요한 위험

- **저장분은 브라우저 하나에 갇힌다.** localStorage 는 사용자 · 브라우저별이라 담당자가
  여럿인 상황을 재현하지 못한다. 실제 운영이라면 서버 트랜잭션과 row lock 이 있어야 하는
  자리다.
- **동시 요청은 한 탭 안에서만 안전하다.** 액션이 `get()` 으로 최신 상태를 다시 읽고
  `set()` 한 번에 대입하므로 한 탭 안에서는 어긋나지 않지만, 같은 상태를 두 탭이 각자
  저장하면 나중에 저장한 쪽이 이긴다.
- **이력은 재고 칸의 변화만 남긴다.** 검사 통과처럼 재고를 움직이지 않는 처리는 이력에
  서지 않고 문서의 검사상태로만 확인한다.
- **시각 검증을 못 했다.** 화면 렌더는 jsdom 테스트로만 확인했고 실제 브라우저 스크린샷은
  찍지 못했다.
